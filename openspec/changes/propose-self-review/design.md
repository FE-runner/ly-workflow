## Context

`/ly:propose` 现有编排（v1.6.0）：worktree 询问 → 全自动/手动询问 → `opsx:propose` 生成方案 → 快照比对定 change 名 → 检查 index → `git add` → 立即 commit `propose: <change-name>` → 按路径分流（全自动流水线 / 手动确认）。产物生成与 commit 之间没有任何自检环节；需求逻辑闭环与业务全面性完全依赖事后的外部审查（review-plan），而外部审查者无 propose 讨论上下文，查"业务不全面"只能撒网。

自审发生在编排层（propose.md），执行者是当前会话 Claude——它刚写完方案，上下文最全，且具备直接修改 artifact 的权限。

## Goals / Non-Goals

**Goals:**

- 方案定稿前由提出者完成闭环与全面性自检，机械问题当场修、业务问题当场问
- 全自动流水线获得一个人工确认点（业务判断类开放问题），其余环节保持无人值守
- 自审结果可核查（逐项结论清单），防止走过场

**Non-Goals:**

- 不升级 `/ly:review-plan` / `plan-reviewer.md`——外部审查维持"一致性 + 风险"职责，不增加闭环/全面性检查项（分工见决策 1）
- 不新增独立 slash command（自审不是用户可单独调用的命令，是 propose 编排的一段）
- 不引入 wrapper 调用、不改任何 TypeScript 源码与 npm 依赖

## Decisions

### 决策 1：作者自审，而非升级外部审查——两问题分工

| 问题性质 | 需要什么 | 谁具备 |
|----------|----------|--------|
| 逻辑闭环、业务全面性 | propose 讨论上下文（需求原话、舍弃的分支、业务约束） | 作者 ✓ 外部 ✗ |
| 文档一致性、风险点 | 独立视角（不被作者思路带着走） | 作者 ✗ 外部 ✓ |

备选方案"给 plan-reviewer.md 增加闭环/全面性 checklist"被否：外部审查者无上下文，全面性检查退化为通用模板撒网，Warning 泛滥且修复要占审查-修复循环的轮数。自审发生在 author 有写权的时刻，机械断链当场修，一次改完，无循环成本。

### 决策 2：自审位置在"快照比对确定 change 名之后、index 检查与 commit 之前"

时序：`opsx:propose` 产物 → 快照比对定名 → **自审**（修复 + 开放问题询问）→ index 检查 → `git add` → commit。

放在 commit 前使自审修复随 `propose:` commit 一次干净落库，review-plan 的审查对象（该 commit）天然包含自审结果，不出现"commit + 未提交修复"混合状态。备选"commit 后自审"被否：会产生混合状态，且自审修复要等 review-plan 的统一提交才落库，时序复杂化。

### 决策 3：发现二分——机械断链直接修，业务判断类必须问

机械断链（漏任务、范围未同步）有客观答案，作者修即可，问了反而打扰；业务判断类（"权限边界场景要不要支持"）答案只存在于用户脑中，作者猜测即越权。两者混处理会导致要么漏问（把业务决策静默做了）要么过度询问（为每个漏任务打断用户）。

**全自动模式下业务判断类仍然问**（用户明确决策）：全自动的本意是省去"要不要继续"类机械确认，不是授权作者替用户做业务决策；该询问与流水线的"需要人工介入"同级，是合法暂停点。

### 决策 4：四项检查的粒度按"条目"对齐

正向/反向闭环按 proposal What Changes 的列表项与 tasks 的 checkbox 粒度逐条映射，不做段落级语义对齐——后者是模糊判断，会产生扯皮式结论。基线波及按基线 spec 的 Requirement 粒度逐条对照。通用维度固定为一张短清单（权限/失败路径/并发/兼容迁移，可按 change 性质增补），每项必须给结论。

### 决策 5：防走过场用"逐项结论清单"硬约束

自审无对抗性，最大风险是退化成"我刚写的，没问题"。约束与 review 循环的"不认可须写反驳理由"同构：每个检查子项必须落一个四值结论（通过/不适用+理由/已修复/待用户决策），silent skip 视为未执行。清单出现在 propose 编排输出中，用户可直接核查。

### 决策 6：checklist 内嵌 propose.md，不抽共享文件

自审 checklist 只有一个消费者（propose.md），内嵌保持单文件可读；抽成 `prompts/` 下的独立文件是为多消费者服务的，此处无必要。review-plan 不消费同一份 checklist（职责不同，见决策 1）。

## Risks / Trade-offs

- [自审走过场，逐项清单流于形式] → 清单硬约束 + 结论必须可核查（"不适用"须有理由）；review-plan 仍作为兜底，漏掉的一致性问题会被外部审查捞出
- [全自动流水线多了一个暂停点，无人值守体验打折] → 仅业务判断类触发，机械断链不打扰；用户明确选择接受此权衡（"全自动模式下这类问题仍然问"）
- [通用维度清单漏掉某业务的特有维度] → 清单是兜底网不是完备网；基线波及检查（逐条对照既有 Requirements）覆盖"该业务历史上想全了的部分"，两者互补
- [自审加长 propose 单次耗时] → 全程同会话内自查自改，无 wrapper 调用与循环，实测开销可忽略
- [New Capabilities 无基线可查，波及检查不适用] → 由通用维度过网兜底；已在 spec 中明确该跳过规则

## Migration Plan

纯模板改动，无运行时状态与数据迁移。安装侧：`npx ly-workflow update` 重装 `/ly:propose` 命令即生效；卸载回滚无残留。
