## Context

`/ly:review-plan` 与 `/ly:review-code` 目前共用同一份 Codex 角色提示词 `templates/prompts/codex/reviewer.md`（"资深代码审查员"人设，checklist 全是 SQL 注入/N+1/race condition 等代码问题）。安装器（`installer.ts`）按模型目录整体拷贝 `templates/prompts/<model>/` 到 `~/.claude/.ly/prompts/<model>/`，新增文件无需改安装逻辑即可随目录一起装上。见 proposal.md - Why。

## Goals / Non-Goals

**Goals:**
- 给 `/ly:review-plan` 一份专属角色提示词，从源头上避免 Codex 拿"代码库未实现"当方案 Critical。
- 给两个命令共用的终止条件补一类"审查对象类型持续系统性误判"的兜底，防止角色提示词修复不彻底或未来出现类似的系统性跑偏时循环无限空转。

**Non-Goals:**
- 不改变 `/ly:review-code` 使用的角色提示词（仍是原 `reviewer.md`），不改变其审查范畴。
- 不改变现有熔断/分歧未决判定的"锚点匹配"规则本身——新增的第 7 类终止条件是独立的补充判定，不替换、不削弱现有判定。
- 不改动全局轮数上限的数值（该数值属于另一个进行中 change `worktree-review-flow-refinement` 的范围）。
- 不引入"误判类别"的固定枚举列表——判定"是否属于同一大类系统性误判"由 Claude 在循环执行时自行判断并说明理由，不在角色提示词或命令文档中预先穷举所有可能的误判类别。

## Decisions

**1. 新建独立角色提示词文件，而非在共用 `reviewer.md` 里加分支说明**
- 备选方案：保留单一 `reviewer.md`，在文件内新增一段"若审查对象是方案文档而非代码，则遵循以下额外约束"。
- 选择新建独立文件的理由：`reviewer.md` 的人设开篇即是"senior code reviewer"，checklist 结构围绕代码质量/安全/性能展开；给它打补丁式地加一段"方案审查模式"说明，容易被角色人设的整体基调稀释，且两种审查场景的 checklist 本身就该完全不同（方案审查关心遗漏边界/范围/文档一致性，代码审查关心注入/并发/性能），合并在一份文件里对两种场景都是噪音。独立文件让每份角色提示词保持单一职责，`review-code.md`/`review-plan.md` 各自引用对应文件即可，改动面也更小（只改 `review-plan.md` 一处 `ROLE_FILE` 引用）。

**2. 新终止条件按"误判理由类别"连续匹配，不要求锚点匹配**
- 备选方案 A：延用现有熔断/分歧未决的"文件+类别+锚点"三元匹配逻辑，只是放宽到"任意 3 轮内出现次数达到阈值"而不要求相邻。
- 备选方案 B：不新增判定条件，只靠角色提示词修复（Goals 里的第一条）解决问题，不加兜底。
- 选择"连续 3 轮、按误判理由类别匹配、不要求锚点"的理由：本次问题的实际表现就是锚点不断变化（每轮换不同的任务条目）但误判的**理由类别**不变（"代码库没实现"）——现有三元匹配机制天然无法收住这类问题，这是本次要补的缺口。要求"连续"（而非"任意 3 轮"）是为了避免误伤——如果系统性误判只是偶发出现、中间夹杂着真实问题被正常修复，说明角色提示词大体有效，不该转人工；只有连续出现才说明角色提示词的约束没有生效或存在新的遗漏场景，需要人工介入排查（很可能是 `plan-reviewer.md` 本身需要再调整）。轮次选 3 而非 2：2 轮太容易被单次巧合触发（且与现有熔断的"相邻两轮"区分度不够），3 轮足以确认是持续性模式，同时不会像"等到全局轮数上限"那样拖得太久。
- 不要求锚点匹配的理由：若要求锚点匹配，就退化为现有熔断/分歧未决机制，无法覆盖"每轮换个位置但误判类型相同"这一真实观察到的模式。

**3. 判定"是否属于同一大类系统性误判"交给 Claude 在循环执行时自行判断，不预先枚举误判类别**
- 备选方案：在角色提示词或命令文档里列出一份"已知误判类别"清单（如"实现状态误判""风格偏好误判"等），供 Claude 比对。
- 选择不枚举的理由：误判类别的具体内容依赖 Codex 实际的跑偏方式，无法穷尽预判；`/ly:review-plan`/`/ly:review-code` 已经要求 Claude 对每条 Critical 写明认可/不认可的理由（见"Critical 需先经 Claude 判断是否认可"Requirement），第 7 类终止条件只是要求 Claude 在这些已有的反驳理由之上，多做一步"最近 3 轮的反驳理由是否指向同一类问题"的比对——这本身就是 Claude 该具备的判断能力，不需要额外预设分类体系，避免分类体系本身过时或覆盖不全。

## Risks / Trade-offs

- **[风险] "同一大类系统性误判"缺乏客观判定标准，可能被 Claude 主观误用（把本该继续修复的问题错误归为同一类而提前放弃）** → 缓解：终止时必须完整列出 3 轮的原始发现与反驳理由（第 7 类终止条件报告要求与"分歧未决"一致），转人工审阅时可以直接核对 Claude 的归类是否合理，一旦发现误用可以人工纠正并继续；这是"防止无限空转"与"防止误伤"之间的权衡，倾向于优先止损。
- **[风险] `plan-reviewer.md` 的约束写得不够穷尽，Codex 换一种说法继续把实现状态当 Critical（例如不说"没实现"而说"缺少实际代码验证"）** → 缓解：第 7 类终止条件本身就是为这种"角色提示词没能完全堵住"的情况兜底——即便约束文字被绕过，只要连续 3 轮的误判理由类别一致，仍会被拦下转人工；人工介入后可以针对具体的绕过方式再补充 `plan-reviewer.md` 的约束。

## Addendum（Codex 第一、二轮审查发现的缺口，本次修复）

- **spec 未纳入审查输入**：checklist 要求 Codex 判断"spec 是否覆盖 proposal 的 What Changes"，但最初的 delta 只要求命令读取 proposal/design/tasks 三份文件，没要求读取该 change 的 delta spec 文件——Codex 无从判断一个它压根没看到的文件。已在 spec delta 与 tasks.md 补上"读取 `specs/**/*.md`"的要求。
- **修复对象未覆盖 spec 文件**：补上"读取 spec"后，若 Codex 真的认可"spec 未覆盖 proposal"这类 Critical，`/ly:review-plan` 的修复对象原本只列了 `proposal.md`/`design.md`/`tasks.md`，不包含 delta spec 文件——这类 Critical 会被判定认可却无法修复，导致下一轮复审重复出现、循环不清零。已把修复对象扩展到 `specs/**/*.md`。
- **终止报告模板未明确覆盖第 7 类**：任务里"新增第 7 类终止条件"和"报告需要展示 3 轮证据"是两件事，前者只改判定逻辑，不会自动带出后者的报告格式改动。已在 tasks.md 里拆成独立任务明确要求。
- **"20 轮"字面数字与当前正式 spec 不一致**：本 change 最初起草时，`openspec/specs/ly-review-gates/spec.md` 的全局轮数上限仍是 20 轮；后来 `worktree-review-flow-refinement` change 已经落地并归档，把该值改成了 5 轮（且新增了"清零优先于轮数上限"的判定顺序）。若继续按最初草稿的"20 轮"字面值合并，会在归档时把已生效的 5 轮改动回退，属于真实的回归风险，不是无关分支的假设性冲突。已按 `openspec/specs/ly-review-gates/spec.md` 当前实际内容（5 轮 + 清零优先）为基线重写该 Requirement 的 delta，只追加新终止条件名，不改动数值和判定顺序。
- **两套独立的终止条件编号体系**：spec 里"审查-修复循环与终止条件"Requirement 自身只列 7 类（不含审查调用失败、全局轮数上限，这两个是独立 Requirement）；命令文件（`review-plan.md`/`review-code.md`）里的"循环终止条件"列表是把全部信号合并展示的完整清单，当前是 1-8（多算了审查调用失败与轮数上限）。新终止条件在 spec 里是第 7 类，在命令文件的合并列表里则是追加到末尾的第 9 类——两处编号不同、不能混用同一个数字，之前的草稿曾把两者混为一谈（写成"触发条件 2-8 改 2-7"），已在 tasks.md 里分开说明。
