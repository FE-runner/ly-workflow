## Context

现状（本次改动前）：`/ly:propose` 的总开关是二元的"要不要走自动化收尾"，选否直接在 commit 后结束，没有任何 worktree/审查入口；选是则自动跑 `review-plan`，只在 Critical 清零时问一次 worktree，其余终止原因（熔断、分歧未决等）直接结束不问。`/ly:apply` 没有任何 worktree 询问。`review-code`/`review-plan` 的全局轮数上限是 20 轮。详见 proposal.md - Why。

设计过程中已经和用户在会话里用 mermaid 流程图逐步核对过三张图（`workflow.md`，非正式文档，仅作参照）：propose 主流程（全自动/手动两分支）、apply 流程、审查-修复循环内部细节。本 design.md 是这些图对应的文字化设计记录。

## Goals / Non-Goals

**Goals:**
- 把 `/ly:propose` 的总开关语义从"是否自动化"改为"全自动 vs 手动逐步确认"两条路径，两条路径下 commit 都无条件执行。
- 手动路径下补上两处 worktree 询问点（方案提交后、审查循环清零后）和一处"要不要跑审查"的询问。
- 无论全自动还是手动路径，审查循环以任一"非清零"原因终止时都问一次 worktree（不带 `--auto`），把非正常终止统一处理为"退出自动模式，回到人工确认"。
- `/ly:apply` 执行前补一次隔离检测+询问。
- 全局轮数上限默认值从 20 降到 5。

**Non-Goals:**
- 不改变 `/ly:worktree switch` 的既有续接命令契约本身（只打印不自动执行、`--auto` 只改文案不改执行方式，见 `worktree-switch` 能力）；本次唯一新增的 `switch` 改动是"定位已注册路径时校验分支"这一处（Decision 10），不涉及路径规则、续接命令格式等其余行为。
- 不引入 `--local` 项目内路径作为受控目标路径的概念——`switch` 目前没有定义过 `--local` 用法，本次不新增（Decision 10）。
- 不改变审查-修复循环内部的判定规则（Critical 认可/不认可、熔断判同键、验证方式等），只改"循环外层"在各终止原因下是否询问 worktree，以及全局轮数上限的数值。
- 不引入新的自动化能力（比如"手动路径下自动生成 change 名再 switch"）——手动路径下 switch 若上下文无法确定 change 名，直接询问用户，不猜测。
- **本次隔离检测的目标是防误操作，不是防故意绕过**（Decision 11）：只保证正常使用路径下（未手工破坏 git 状态）不会把改动误写到错误分支/错误 worktree；不承诺能挡住用户故意手工操作 git（如把目标分支 reset 到无关提交、手工伪造固定路径下的分支）绕过检测，也不强制 `/ly:worktree switch` 的续接命令必须经过 `/ly:apply`（续接提示仍是建议性引导，不是强制约束）。

## Decisions

**1. 总开关从"是否自动化"改为"全自动 vs 手动"两条路径，而不是加更多独立开关**
- 备选方案：给 propose 加三四个独立的 `AskUserQuestion`（要不要 review？要不要 worktree？要不要 auto？），互相正交组合。
- 选择两条路径的理由：正交组合会在手动模式下问太多次、顺序关系复杂（比如"要不要 worktree"和"要不要 review"哪个先问、选了 worktree 是否还要继续问 review）。收敛成"全自动"（保持现状不变）和"手动"（逐步确认，路径内部顺序固定）两条路径，逻辑分支数量可控，且完全不破坏现有全自动路径的用户习惯。

**2. 手动路径下选择切换 worktree 后直接结束编排，不追问是否要审查**
- 备选方案：即使切了 worktree，仍然接着问"要不要跑 review-plan"。
- 选择直接结束的理由：worktree switch 只打印续接命令、不跨会话执行（见 `worktree-switch` 能力），当前会话在这之后已经不适合继续做决策——用户会到新 worktree 里开一个新会话继续，那时候的"要不要审查"应该由那个新会话/新上下文决定，propose 在当前会话里问也白问（回答不会被新会话感知）。

**3. 非清零终止原因下，全自动/手动路径都问 worktree，但一律不带 `--auto`**
- 备选方案 A：非清零终止原因也不问（维持改动前行为）。
- 备选方案 B：非清零终止原因问，且沿用当前路径的 `--auto` 设置（全自动路径带，手动路径不带）。
- 选择"都问、都不带 `--auto`"的理由：用户明确要求"其余原因结束都要问，本质是非正常状态退出自动状态"——非清零终止意味着方案/代码本身还没收敛，即使去了隔离环境也需要人工先看一眼再决定下一步，不应该自动续跑 `/ly:review-code` 循环（那样等于在问题未确认前又自动跑了一轮，违背"退出自动模式"的意图）。所以不管是从全自动路径还是手动路径进入这个分支，`--auto` 都不带。

**4. `/ly:apply` 的隔离检测复用 `/ly:worktree` Add 步骤已有的判定逻辑**
- 具体做法：比较 `git rev-parse --git-dir` 与 `--git-common-dir`，不同则已在 worktree 内（同时用 `--show-superproject-working-tree` 排除子模块误判）。
- 理由：这个判定逻辑已经在 `worktree.md` 里实现并验证过，直接复用而不是重新发明一套检测方式；也保证"已在 worktree 内"这个概念在整个能力集里是同一个定义。

**5. 全局轮数上限 20→5，只改数值，不改判定逻辑**
- 理由：正常场景 2-3 轮就该清零或熔断，20 轮的兜底价值不大且拖长转人工前的等待；5 轮仍然留有余量（覆盖"正常 2-3 轮 + 一点缓冲"），不改变熔断/分歧未决等主要终止信号的判定方式，纯粹是防真正死循环的最后防线数值调整。
- 清零优先于轮数上限：若第 N 轮（含第 5 轮）审查结果本身是 Critical 清零，按正常清零处理；轮数上限的检查发生在"本轮审查结果非清零"之后，不会把恰好在第 5 轮清零的场景误报为"达到上限"（Codex 审查发现的边界缺口，本次修复）。

**6. `switch` 后追加"运行 /ly:apply 继续"提示，而不是修改 `worktree-switch` 能力本身的续接命令模板**
- 备选方案：修改 `worktree-switch` 的续接命令模板，让它直接输出 `/ly:apply <change-name>` 而不是"读取 tasks.md 按任务执行"。
- 选择在 `propose`/`apply` 自己的输出里追加一句提示的理由：`worktree-switch` 是独立能力，续接命令模板要同时服务于"纯手动实施"（用户可能不想经过 `/ly:apply` 这层）和"走 `/ly:apply` 自动 commit"两种用法，不应该被本次改动收窄为只服务后者；在调用方（propose/apply）自己的输出里加一句提示，既不改变 `worktree-switch` 的既有契约，也解决了"用户切了 worktree 之后不知道该不该走 `/ly:apply`"这个真实缺口（Codex 审查 Critical，本次修复）。

**7. `/ly:apply` 的匹配判定用"当前 worktree 是否位于该 change 的固定目标路径，且该路径注册的分支严格等于 change 名"，而不是"分支名 + 任意已注册路径"**
- 备选方案 A：模糊描述为"当前分支名或所在路径与目标 change 名对应"，留给实现者自行判断，无法判断时默认跳过询问。
- 备选方案 B（第三轮修复采用）：只用"当前分支名是否严格等于 `<change-name>`"单一条件判定。
- 备选方案 C（第四轮修复采用）：分支名严格相等 AND 当前路径等于该分支在 `git worktree list --porcelain` 里注册的路径（不要求该路径是"固定目标路径"，只要求"这个分支确实挂在这个路径上"）。
- 选择"绑定到固定目标路径"的理由：Codex 第五轮指出方案 C 仍有漏洞——用户可以在任意路径手工创建 worktree 并检出同名分支，Git 同样会把该路径注册为这个分支的挂载点，两个条件依然成立，规则仍会静默放过。`/ly:worktree switch <change-name>` 创建/挂载该 change 的 worktree 时使用的路径是确定的（`../.ly/<项目名>/<change-name>`），把这个"固定目标路径"本身作为判定基准，而不是"任意已注册路径"，才能排除"手工在别处挖同名分支"这个残留风险——因为固定目标路径是由 `switch` 的既有路径规则决定的，用户无法随意伪造。
- 目标 change 名的解析也据此补全反查算法：无参数时，枚举未归档 change，对每个候选按"是否等于该候选的固定目标路径"筛选当前 worktree 根路径，恰好一个匹配才采用，否则视为反查失败继续走下一优先级（Codex 第五轮 Warning，本次修复；上一轮遗留的"'当前 worktree 已受控映射'定义存在循环表述"问题也随之解决）。

**8. `switch` 的结果统一按"是否最终输出续接命令"二分判定，续接提示按"是否带 --auto"和"是否有 baseline 失败摘要"两个维度组合，而不是简单叠加**
- 备选方案：分别处理"前置校验拒绝"和"baseline 失败"两类拒绝，各自定义是否算失败、是否输出续接提示；提示文案上"运行 `/ly:apply` 继续"与"实施完成后自动依次调用 `/ly:review-code`"各自独立追加。
- 选择二分判定 + 组合提示的理由：Codex 指出 `worktree-switch` 能力里 baseline 是 worktree 已创建后才运行的验证，失败时会询问用户是否仍要继续，用户选择继续后 `switch` 仍会输出续接命令（携带失败摘要）——这与"前置校验拒绝"（直接报错、完全不产生续接命令）在结果形态上不同，统一以`switch` 最终是否输出了续接命令为判定依据能同时覆盖两者。提示文案上，`--auto` 与 baseline 失败摘要是两个独立维度，可能同时出现：第四轮把两者简单合并成一条说明后，第五轮 Codex 指出这会在"带 `--auto` 且 baseline 失败但用户选择继续"这个交叉场景下丢失"先处理 baseline 问题"的安全提示；改为按四种组合（不带 `--auto`/带 `--auto` × 无失败摘要/有失败摘要）分别定义最终文案，确保"先处理 baseline"和"完成后自动审查"两个约束在交叉场景下都不丢失。

**9. 不引入机器可读的终止状态枚举（对应 Codex Warning：终止状态判定缺少稳定接口）**
- Codex 建议给 `ly-review-gates` 加固定的终止状态枚举/机器可读标记，避免 propose 靠"理解自然语言报告"来判断走哪个分支。
- 不认可，理由：本仓库里所有跨命令的状态传递（`review-plan`/`review-code` 的终止报告、`worktree switch` 的成功/失败、`apply`/`archive` 的 commit 结果）都是同一个 Claude Code 会话在执行多个 slash command，靠 Claude 本身理解上一步产出的自然语言报告来决定下一步，不是程序间的黑盒 API 调用；`ly-review-gates` 已经要求"必须明确指出触发的具体条件"，这个约束对"同一个 agent 读自己刚生成的报告"这个场景已经足够可靠。引入机器可读枚举是给整个 `/ly:*` 命令集换一套状态传递协议的架构级改动，影响面远超本次"worktree 询问点 + 轮数上限"的范围，留作后续独立 change 的候选项，不在这里处理。

**10. 扩大范围，把 `switch` 定位已注册路径时的分支校验纳入本次改动，同时放弃 `--local` 固定路径的说法**
- 背景：Decision 7/8 在 `/ly:apply` 侧堆了好几轮匹配规则（分支名 → 分支名+任意注册路径 → 分支名+固定目标路径），但这些保护全部建立在"`switch` 输出续接命令"这个信号可信"的假设上。Codex 第六轮指出该假设本身不成立：`switch` 现有契约里，只要目标固定路径"已是已注册的 worktree"就直接定位、跳过分支拓扑校验，从未检查这个路径当前挂的是不是 `<change-name>` 分支——如果这个固定路径被别的分支占用（比如历史遗留、或用户手工操作），`switch` 依然会"成功"输出续接命令，把 `/ly:apply` 侧再精细的匹配规则都绕开了，因为 `/ly:apply` 是在"已经切换过去之后"才做检查，而这个绕过发生在"切换"这一步本身。
- 备选方案 A：维持 Non-Goals 里"不改 `switch` 契约"的边界，把这个残留风险记入已知限制，不再展开。
- 备选方案 B（采纳）：把"`switch` 定位已注册路径时校验分支"补进本次范围，作为对 `worktree-switch` 能力的一处小改动（见该能力的 delta spec），不等于全面重新设计 `switch`。
- 选择 B 的理由：这不是一个"锦上添花"的边界完善，而是"如果不修，`/ly:apply` 前面几轮加的全部保护实质上不生效"的根本性缺口——保护链条里最薄弱的一环恰好在调用链最前面（`switch` 本身），后面加多少层校验都补不上。范围扩大控制在最小必要修改：只加一处分支校验，不改 `switch` 的路径规则、续接命令格式、`--auto` 语义等其余行为。
- `--local` 路径同时被放弃：本次改动过程中"该 change 的固定目标路径"曾经包含"默认路径 + `--local` 路径"两种，但 `switch` 现有契约根本没有定义过 `--local` 参数（`--local` 是 `add` 子命令的选项，`switch` 的选项只有 `[--auto]`），继续在文档里描述一个不存在的用法只会制造新的不一致。改为只承认默认路径，`--local` 场景留给未来若真要支持时再单独设计和验证。
- 固定目标路径的解析统一以 `git rev-parse --git-common-dir` 找到主仓库位置作为基准，不依赖调用发生时所处 worktree 的相对路径推导——避免"从另一个 worktree 里调用 switch/apply"时算出不一致的目标路径（Codex 第七轮 Critical，本次修复）。

**11. 明确本次隔离检测的目标是防误操作，不是防故意绕过；对第七轮提出的三个更深层 Critical 分别判定**
- Codex 第七轮在"分支名 + 固定路径都匹配"的基础上继续提出三个更深的问题：（a）分支名匹配不代表该分支的 `HEAD` 真的包含目标 change 的 artifact，用户可以把分支 reset 到无关提交；（b）`switch` 的续接命令本身不强制经过 `/ly:apply`，用户仍可以直接手动实施绕开自动 commit；（c）"主仓库根"的解析在"从另一个 worktree 调用"时可能不一致。
- （a）（b）判定为**不认可，超出本次范围**：
  - （a）要求校验才能证明"这个 worktree 里真的是这个 change 的最新方案"，这已经不是"防误用同名分支"的范畴，而是要求整套机制能防"用户故意破坏本地 git 状态"——这类攻击面在纯本地、无服务端强制的 Git 工作流里本质上无法通过 client-side 检测完全堵死（用户随时可以 `git checkout`、`reset`、手工编辑文件），继续加码校验只是把"打地鼠"往更深处推，边际收益迅速递减。
  - （b）`/ly:worktree switch` 被设计成通用的隔离环境切换工具，续接命令是建议性文本，不是所有 OpenSpec change 都必须经过 `/ly:apply` 实施；本次已经在续接提示里加了明确引导（"运行 `/ly:apply` 继续"），这是本次范围内合理的改进幅度——把它做成"强制"需要重新设计 `switch` 的续接机制（比如加一个只能触发 `/ly:apply` 的专用参数），这是比"分支校验"更大的架构变动，不在本次范围内。
  - 两者都记入下方 Risks，作为已知的、有意接受的限制，不阻塞进入实施阶段。
- （c）判定为**认可，本次修复**：路径解析基准不一致属于实现正确性问题（会导致算法本身在某些合法场景下跑错，不是"防绕过"的边际情况），影响的是"正常使用路径下会不会误判"，属于本次"防误操作"的目标范围。已在 Decision 10 补充统一解析规则。
- Codex 第七轮的 Warning（"`/ly:apply` 侧直接读取 switch 定位结果"这句表述与"读取 `git worktree list --porcelain`"自相矛盾）判定为**认可，本次修复**：纯粹是文字表述问题，删除"读取 switch 定位结果"的说法，改为"`/ly:apply` 每次独立读取当前 canonical 路径与 `git worktree list --porcelain` 完成判定"。

## Risks / Trade-offs

- [手动路径分支变多，命令说明文字变长，用户第一次用可能觉得繁琐] → 通过总开关询问文案里说清楚"全自动=自动审查+清零后问一次worktree+隔离后自动续接；手动=每一步都问"，让用户在选择前就知道会问几次。
- [全局轮数上限从 20 降到 5 后，理论上更容易在复杂 change 上碰到"达到轮数上限"而不是正常收敛] → 5 轮仍然是"正常 2-3 轮"的将近 2 倍余量；命中该上限本身就是设计好的兜底终止条件，报告会给出完整轮次轨迹，不是静默失败。
- [`/ly:apply` 新增的隔离检测在极端场景下误判（比如子模块）] → "是否在任意 worktree 内"直接复用 `worktree.md` 里已经处理过子模块误判的同一段检测逻辑，不重新实现；"是否匹配目标 change"绑定到该 change 的固定目标路径，并由 `switch` 自身校验该路径的分支（Decision 7、10），排除"手工在任意路径检出同名分支"或"固定路径被占用"这类假阳性，降低出现新 bug 的面。
- [不引入机器可读终止状态枚举（Decision 9），未来报告格式演进时理论上仍有误判风险] → 接受该风险：这是本次改动范围内的有意取舍，不是遗漏；若后续确实出现因报告格式变化导致误判的真实案例，再单独立项处理。
- [范围扩大到 `worktree-switch` 能力后，改动面比最初设想更大] → 已控制在最小必要修改（只加一处分支校验），且该能力自身的其余 Requirement/Scenario 均未改动；`openspec validate` 持续通过，未引入结构性风险。
- [分支名+路径匹配不校验目标分支 `HEAD` 是否真的包含该 change 当前的 artifact，用户可以手工把分支 reset 到无关提交后绕过检测] → 有意接受（Decision 11）：这是"防误操作"范围之外的"防故意绕过"场景，client-side 检测本质上无法完全堵死用户主动破坏本地 git 状态；不为此增加 artifact commit 可达性校验这类更重的检查。
- [`/ly:worktree switch` 的续接命令仍只是建议性引导用户运行 `/ly:apply`，不是强制约束，用户仍可以手动实施绕过 apply 的自动 commit] → 有意接受（Decision 11）：`switch` 被设计为通用的隔离环境切换工具，不是所有 change 都必须经过 `/ly:apply`；把引导升级为强制需要重新设计 `switch` 的续接机制，是比本次范围更大的架构变动，留作后续独立 change 的候选项。
